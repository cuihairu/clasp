# Source Architecture

- [Glossary](./glossary.md)
- [中文架构解说](/zh/reference/architecture)

This is a source-derived description of Clasp's responsibilities, state, configuration, lifecycle, and call paths. It deliberately describes responsibility layers rather than directory names.

## 1. Contract, Build, And Packaging

The build contract defines C++17, verifies that the project version and `CLASP_VERSION_*` macros agree, compiles the small non-header translation units, and exports a CMake package as `clasp::clasp` (`CMakeLists.txt:2`, `CMakeLists.txt:4`, `CMakeLists.txt:11`, `CMakeLists.txt:39`, `CMakeLists.txt:52`, `CMakeLists.txt:61`, `CMakeLists.txt:77`). Its schema is the CMake input `CLASP_BUILD_EXAMPLES` plus `CLASP_ENABLE_COVERAGE`, together with standard install directories and shared-library settings (`CMakeLists.txt:23`, `CMakeLists.txt:27`, `CMakeLists.txt:54`, `CMakeLists.txt:63`). The public include tree and package config are the consumer-facing interface (`CMakeLists.txt:46`, `CMakeLists.txt:70`, `cmake/claspConfig.cmake.in:3`).

State is build metadata and installed artifacts, not runtime state. Examples and tests are opt-in consumer contracts: when enabled, the same layer builds executables, registers CTest cases, and locks user-visible strings and parsing behavior (`CMakeLists.txt:93`, `CMakeLists.txt:100`, `CMakeLists.txt:2340`, `CMakeLists.txt:2380`). The vcpkg draft supplies an alternate packaging entry point and currently pins its draft to `v0.1.0` (`packaging/vcpkg/portfile.cmake:1`, `packaging/vcpkg/portfile.cmake:4`, `packaging/vcpkg/README.md:3`).

## 2. Command Tree And Application Model

`Command` is the in-memory application model. It owns names, aliases, metadata, groups, local and persistent flags, child ownership, streams, callbacks, overrides, context, and presentation/completion settings (`include/clasp/command.hpp:69`, `include/clasp/command.hpp:354`, `include/clasp/command.hpp:232`, `include/clasp/command.hpp:3189`). `Flag` is the declarative flag metadata record, including long/short names, description, typed default, required/hidden/deprecated state, annotations, and no-value default (`include/clasp/flag.hpp:23`, `include/clasp/flag.hpp:61`). The compatibility header only forwards to the canonical command header (`include/clasp/command.h:4`).

The tree's storage is process-local memory. `addCommand` transfers a value into a uniquely owned child and immediately reparents it (`include/clasp/command.hpp:354`), while the hand-written move constructor and assignment keep child `parent_` pointers valid across ownership transfer (`include/clasp/command.hpp:73`, `include/clasp/command.hpp:150`). Configuration is entered by builder methods rather than an external schema: aliases and annotations (`include/clasp/command.hpp:337`), flags and typed flag helpers (`include/clasp/command.hpp:372`, `include/clasp/command.hpp:385`), hooks and actions (`include/clasp/command.hpp:52`), command/flag constraints (`include/clasp/command.hpp:1070`), templates and output streams (`include/clasp/command.hpp:1263`, `include/clasp/command.hpp:232`), and context (`include/clasp/command.hpp:1319`).

## 3. Execution Orchestration

`run`, `execute`, command resolution, validation, and hook/action sequencing form the runtime boundary. `execute()` can synthesize `argv` from a previously supplied vector, then both entry points call `run` (`include/clasp/command.hpp:1360`, `include/clasp/command.hpp:1374`). `resolveForExecution` walks raw tokens through aliases and subcommands and records whether the resolved path means help or version (`include/clasp/command.hpp:3034`, `include/clasp/command.hpp:3175`).

After resolution, `run` constructs a resolved-command `Parser`, applies parser options from inherited command overrides, routes parse and color failures through the selected error formatter, and dispatches help/version before external source and bound-value application (`include/clasp/command.hpp:1376`, `include/clasp/command.hpp:1396`, `include/clasp/command.hpp:1412`, `include/clasp/command.hpp:1444`). It then validates positional arguments, required flags, flag groups, and deprecated state before invoking the resolved command (`include/clasp/command.hpp:1437`, `include/clasp/command.hpp:1461`, `include/clasp/command.hpp:1467`, `include/clasp/command.hpp:1487`). Hook execution walks the parent chain, runs persistent pre-hooks, local pre-hooks, one action form, then post-hooks in reverse ownership order (`include/clasp/command.hpp:2555`). The return channel is an integer process exit status; user actions may use either an integer or an error-message action (`include/clasp/command.hpp:52`).

## 4. Token Parsing, Values, And Validation

`Parser` owns one invocation's decoded flag state. Its `Options` configure unknown flags, short grouping, boolean negation, suggestions, raw mode, and key normalization (`include/clasp/parser.hpp:30`). Construction registers built-ins and declared aliases/kinds/defaults, then decodes `--`, `--key=value`, short groups, inline short values, and separate values into ordered occurrences (`include/clasp/parser.hpp:44`, `include/clasp/parser.hpp:1274`, `include/clasp/parser.hpp:1352`). Unknown flags receive Levenshtein suggestions through the shared utility (`include/clasp/parser.hpp:1437`, `include/clasp/utils.hpp:13`, `include/clasp/utils.hpp:33`).

The canonical runtime state is in-memory maps for explicit values, external scalar/multi values, aliases, kinds, defaults, no-value defaults, extension keys, and positionals (`include/clasp/parser.hpp:1447`). Accessors make precedence explicit: explicit CLI values first, then external multi/scalar values, then declared defaults (`include/clasp/parser.hpp:217`). The typed extension callback is deliberately applied only after external merge; `Command::applyBoundFlagValues` reads explicit values and calls `Value::set` in occurrence order (`include/clasp/value.hpp:13`, `include/clasp/command.hpp:3645`).

Type validation starts from the default's variant kind and specializes string keys through truthy annotations (`include/clasp/parser.hpp:644`, `include/clasp/parser.hpp:1274`). `normalizeValue` then validates and canonicalizes booleans, integers of several widths, floats, durations, IP/mask/CIDR values, URLs, byte sizes, IP slices, and Base64 (`include/clasp/parser.hpp:1125`). Primitive number/duration parsing is isolated in `detail/value_parse.hpp`; strict Base64 encode/decode is also isolated there (`include/clasp/detail/value_parse.hpp:25`, `include/clasp/detail/value_parse.hpp:188`). `Flag::convertToFlagValue` adapts the same primitives into the public `FlagValue` variant (`src/flag.cpp:8`, `include/clasp/flag.hpp:13`).

## 5. External Source Integration

The external-source layer converts environment and file values into already-validated parser state. Environment mappings are command-tree metadata merged child-over-parent (`include/clasp/command.hpp:322`, `include/clasp/command.hpp:3635`). A config path can be fixed or supplied through a normalized flag (`include/clasp/command.hpp:327`, `include/clasp/command.hpp:332`).

`applyExternalSources` reads an env-like scalar format and four structured formats with small in-header parsers: JSON with a nesting-depth guard, YAML, TOML, and INI/CFG (`include/clasp/command.hpp:3690`, `include/clasp/command.hpp:3714`, `include/clasp/command.hpp:4205`). It flattens keys into long-flag aliases, including bare, underscore, dotted, and `varName` forms (`include/clasp/command.hpp:4240`), then inserts validated multi and scalar values (`include/clasp/command.hpp:4282`). Process environment variables override config values; the access helper is the platform boundary (`include/clasp/command.hpp:4272`, `include/clasp/color.hpp:46`). Thus the documented runtime precedence is CLI, environment, config file, then default (`docs/guide/config.md:3`). State is file content and process environment read during a run; there is no daemon, database, or network source.

## 6. Presentation, Export, And Terminal Adaptation

Presentation turns resolved command/flag state into user-visible help, usage, version, Markdown, and roff output. Help rendering gathers visible commands and local/global flags, honors function or template overrides, and supports a small placeholder template language rather than Go templates (`include/clasp/command.hpp:1494`, `include/clasp/command.hpp:2429`, `include/clasp/command.hpp:2318`). Usage follows the same override chain (`include/clasp/command.hpp:1904`), while Markdown and manpage export are separate text protocols (`include/clasp/command.hpp:1545`, `include/clasp/command.hpp:1584`). Output sinks are inherited or locally overridden `ostream` references (`include/clasp/command.hpp:1935`).

The color adapter encapsulates terminal capability, ANSI sequences, themes, `NO_COLOR`, `TERM=dumb`, and Windows VT mode (`include/clasp/color.hpp:66`, `include/clasp/color.hpp:78`, `include/clasp/color.hpp:88`, `include/clasp/color.hpp:95`, `src/color.cpp:14`, `src/color.cpp:32`). Presentation decides whether to style output using the color owner's runtime mode and the adapter (`include/clasp/command.hpp:2138`, `include/clasp/command.hpp:2152`). Color mode/theme may also come from persistent CLI flags; raw arguments are pre-scanned only until a subcommand boundary, then parser values are applied after normal parsing (`include/clasp/command.hpp:246`, `include/clasp/command.hpp:2185`, `include/clasp/command.hpp:2209`). Text is the channel: `stdout`, `stderr`, caller-owned streams, ANSI, Markdown, and roff.

## 7. Completion Protocol And Shell Generation

Completion has two cooperating surfaces. At command-tree setup, `enableCompletion` installs a user-facing script generator plus hidden dynamic commands according to `CompletionConfig` (`include/clasp/command.hpp:1626`, `include/clasp/command.hpp:4560`). The generated scripts call those hidden commands through the shell's normal process invocation channel (`include/clasp/command.hpp:4581`, `include/clasp/command.hpp:4606`).

The dynamic path receives shell words as `argv`, resolves the command that would execute, consults traversal-aware flag metadata and callbacks, and emits values and descriptions (`include/clasp/command.hpp:2635`, `include/clasp/command.hpp:2723`, `include/clasp/command.hpp:2815`). Directives are a Cobra-compatible numeric bitmask (`include/clasp/command.hpp:37`); filename and directory helpers turn extensions or directories into directive-producing callbacks (`include/clasp/command.hpp:997`, `include/clasp/command.hpp:1015`). Static generator output covers Bash/Zsh through one internal generator, plus Fish and PowerShell, with shell-specific escaping helpers (`include/clasp/command.hpp:1618`, `include/clasp/command.hpp:3379`, `include/clasp/command.hpp:4291`, `include/clasp/command.hpp:4449`). The protocol files are generated at runtime rather than checked in as a dedicated protocol source.

## 8. Consumer Verification And Documentation Contract

Examples are small executable demonstrations of the model, execution, typed values, completion, external sources, and documentation export (`examples/basic_example.cpp:7`, `examples/completion_example.cpp:6`, `examples/config_json_example.cpp:7`, `examples/docs_example.cpp:7`). Unit and integration tests directly call `Command` and `Parser`, inject streams, and execute the resulting CLI rather than testing private internals (`tests/completion.cpp:13`, `tests/config_parse_coverage.cpp:64`, `tests/execute.cpp:7`). CMake turns examples into external black-box tests and pins exact messages for Cobra-compatible behavior (`CMakeLists.txt:97`, `CMakeLists.txt:2340`).

The documentation site is the human-facing projection of that contract. English and Chinese guides describe commands, flags, completion, config precedence, templates, and custom `Value` types (`docs/guide/index.md:3`, `docs/zh/guide/index.md:3`), while VitePress wires both locales and excludes raw review archives (`docs/.vitepress/config.ts:5`, `docs/.vitepress/config.ts:15`, `docs/.vitepress/config.ts:8`). The cross-language content is synchronized by intent, and this architecture page plus its glossary now provide the source-derived abstract model.

## Splitting Rationale

1. **Separate declarations from an invocation's decoded result.** `Flag` is retained command metadata (`include/clasp/flag.hpp:61`), while `Parser` records ordered runtime occurrences separately (`include/clasp/parser.hpp:1447`). Mixing them would blur persistent tree ownership with per-run state.
2. **Keep command ownership and parent resolution in one invariant.** Moving a `Command` must rewrite every child's parent pointer; the custom move and `reparent` path exist because normal member-wise movement would leave dangling parents (`include/clasp/command.hpp:73`, `include/clasp/command.hpp:354`, `include/clasp/command.hpp:2630`).
3. **Resolve the executing node before constructing a parser.** `resolveForExecution` consumes command tokens and returns command-specific `argv` (`include/clasp/command.hpp:3034`, `include/clasp/command.hpp:3078`), while `Parser` then parses only that node's effective flags (`include/clasp/command.hpp:1396`, `include/clasp/command.hpp:1405`). This makes inherited semantics and command-local positionals independent.
4. **Make source precedence observable at the accessor boundary.** `getFlag` explicitly consults CLI, external multi, external scalar, and defaults in that order (`include/clasp/parser.hpp:217`), and docs expose the same precedence (`docs/guide/config.md:3`). A hidden merge layer would make override behavior hard to reason about.
5. **Apply custom `Value` callbacks after all source merging.** The contract says `set()` sees final effective values in occurrence order (`include/clasp/value.hpp:13`), and execution applies bindings only after external sources (`include/clasp/command.hpp:1444`, `include/clasp/command.hpp:3645`). Earlier callbacks would break config/env-aware custom types.
6. **Treat generated scripts and dynamic completion as one protocol, not four unrelated outputs.** All generated shells ultimately call configured `__complete`/`__completeNoDesc` commands (`include/clasp/command.hpp:4560`, `include/clasp/command.hpp:4581`, `include/clasp/command.hpp:4606`), while `completeWords` resolves context once (`include/clasp/command.hpp:2815`). Shell-specific generators can then vary only syntax and escaping.
7. **Isolate platform and text-format details.** Terminal capability is confined to `color` (`src/color.cpp:14`, `src/color.cpp:32`); numeric/Base64 primitives to `detail/value_parse.hpp` (`include/clasp/detail/value_parse.hpp:25`, `include/clasp/detail/value_parse.hpp:188`); and file syntax parsing to `applyExternalSources` (`include/clasp/command.hpp:3673`, `include/clasp/command.hpp:4205`). Command orchestration does not need each platform rule inline.
8. **Pin externally visible text through executable consumer contracts.** CMake builds examples and asserts exact Cobra-compatible help/error strings (`CMakeLists.txt:2340`, `CMakeLists.txt:2344`, `CMakeLists.txt:2353`), while tests exercise in-process behavior (`tests/execute.cpp:7`, `tests/completion.cpp:13`). This keeps compatibility concerns separate from implementation organization.
