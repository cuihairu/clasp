# Source Architecture

- [Glossary](./glossary.md)
- [中文架构解说](/zh/reference/architecture)

This is a source-derived description of Clasp's responsibilities, state, configuration, lifecycle, and call paths. It deliberately describes responsibility layers rather than directory names.

## 1. Contract, Build, And Packaging

The build contract defines C++17, verifies that the project version and `CLASP_VERSION_*` macros agree, compiles the small non-header translation units, and exports a CMake package as `clasp::clasp` (`CMakeLists.txt:2`, `CMakeLists.txt:4`, `CMakeLists.txt:11`, `CMakeLists.txt:39`, `CMakeLists.txt:50`, `CMakeLists.txt:59`, `CMakeLists.txt:75`). Its schema is the CMake input `CLASP_BUILD_EXAMPLES` plus `CLASP_ENABLE_COVERAGE`, together with standard install directories and shared-library settings (`CMakeLists.txt:23`, `CMakeLists.txt:27`, `CMakeLists.txt:52`, `CMakeLists.txt:61`). The public include tree and package config are the consumer-facing interface (`CMakeLists.txt:44`, `CMakeLists.txt:68`, `cmake/claspConfig.cmake.in:3`).

State is build metadata and installed artifacts, not runtime state. Examples and tests are opt-in consumer contracts: when enabled, the same layer builds executables, registers CTest cases, and locks user-visible strings and parsing behavior (`CMakeLists.txt:91`, `cmake/tests.cmake:5`, `cmake/examples.cmake:401`, `cmake/examples.cmake:406`). The vcpkg draft supplies an alternate packaging entry point and pins `v0.1.2` with a filled `SHA512` (`packaging/vcpkg/portfile.cmake:1`, `packaging/vcpkg/portfile.cmake:4`, `packaging/vcpkg/README.md:3`).

## 2. Command Tree And Application Model

`Command` is the in-memory application model. It owns names, aliases, metadata, groups, local and persistent flags, child ownership, streams, callbacks, overrides, context, and presentation/completion settings (`include/clasp/command.hpp:71`, `include/clasp/command.hpp:220`, `include/clasp/command.hpp:92`, `include/clasp/command.hpp:3199`). `Flag` is the declarative flag metadata record, including long/short names, description, typed default, required/hidden/deprecated state, annotations, and no-value default (`include/clasp/flag.hpp:23`, `include/clasp/flag.hpp:61`). The compatibility header only forwards to the canonical command header (`include/clasp/command.h:4`).

The tree's storage is process-local memory. `addCommand` transfers a value into a uniquely owned child and immediately reparents it (`include/clasp/command.hpp:220`), while the hand-written move constructor and assignment keep child `parent_` pointers valid across ownership transfer (`include/clasp/command.hpp:83`, `include/clasp/command.hpp:87`). Configuration is entered by builder methods rather than an external schema: aliases and annotations (`include/clasp/command.hpp:203`), flags and typed flag helpers (`include/clasp/command.hpp:238`, `include/clasp/command.hpp:251`), hooks and actions (`include/clasp/command.hpp:54`), command/flag constraints (`include/clasp/command.hpp:966`), templates and output streams (`include/clasp/command.hpp:1165`, `include/clasp/command.hpp:92`), and context (`include/clasp/command.hpp:1218`).

## 3. Execution Orchestration

`run`, `execute`, command resolution, validation, and hook/action sequencing form the runtime boundary. `execute()` can synthesize `argv` from a previously supplied vector, then both entry points call `run` (`include/clasp/command.hpp:1256`, `include/clasp/command.hpp:1270`). `resolveForExecution` walks raw tokens through aliases and subcommands and records whether the resolved path means help or version (`include/clasp/command.hpp:2954`, `include/clasp/command.hpp:3101`).

After resolution, `run` constructs a resolved-command `Parser`, applies parser options from inherited command overrides, routes parse and color failures through the selected error formatter, and dispatches help/version before external source and bound-value application (`include/clasp/command.hpp:1287`, `include/clasp/command.hpp:1310`, `include/clasp/command.hpp:1326`, `include/clasp/command.hpp:1359`). It then validates positional arguments, required flags, flag groups, and deprecated state before invoking the resolved command (`include/clasp/command.hpp:1352`, `include/clasp/command.hpp:1376`, `include/clasp/command.hpp:1382`, `include/clasp/command.hpp:1402`). Hook execution walks the parent chain, runs persistent pre-hooks, local pre-hooks, one action form, then post-hooks in reverse ownership order (`include/clasp/command.hpp:2482`). The return channel is an integer process exit status; user actions may use either an integer or an error-message action (`include/clasp/command.hpp:54`).

## 4. Token Parsing, Values, And Validation

`Parser` owns one invocation's decoded flag state. Its `Options` configure unknown flags, short grouping, boolean negation, suggestions, raw mode, and key normalization (`include/clasp/parser.hpp:31`). Construction registers built-ins and declared aliases/kinds/defaults, then decodes `--`, `--key=value`, short groups, inline short values, and separate values into ordered occurrences (`include/clasp/parser.hpp:45`, `include/clasp/parser.hpp:759`, `include/clasp/parser.hpp:860`). Unknown flags receive Levenshtein suggestions through the shared utility (`include/clasp/parser.hpp:940`, `include/clasp/utils.hpp:13`, `include/clasp/utils.hpp:33`).

The canonical runtime state is in-memory maps for explicit values, external scalar/multi values, aliases, kinds, defaults, no-value defaults, extension keys, and positionals (`include/clasp/parser.hpp:950`). Accessors make precedence explicit: explicit CLI values first, then external multi/scalar values, then declared defaults (`include/clasp/parser.hpp:223`). The typed extension callback is deliberately applied only after external merge; `Command::applyBoundFlagValues` reads explicit values and calls `Value::set` in occurrence order (`include/clasp/value.hpp:13`, `include/clasp/command.hpp:3491`).

Type validation starts from the default's variant kind and specializes string keys through truthy annotations (`include/clasp/parser.hpp:625`, `include/clasp/parser.hpp:759`). `normalizeValue` then validates and canonicalizes booleans, integers of several widths, floats, durations, IP/mask/CIDR values, URLs, byte sizes, IP slices, and Base64 (`include/clasp/parser.hpp:629`). Primitive number/duration parsing is isolated in `detail/value_parse.hpp`; strict Base64 encode/decode is also isolated there (`include/clasp/detail/value_parse.hpp:25`, `include/clasp/detail/value_parse.hpp:188`). `Flag::convertToFlagValue` adapts the same primitives into the public `FlagValue` variant (`src/flag.cpp:8`, `include/clasp/flag.hpp:13`).

## 5. External Source Integration

The external-source layer converts environment and file values into already-validated parser state. Environment mappings are command-tree metadata merged child-over-parent (`include/clasp/command.hpp:188`, `include/clasp/command.hpp:3481`). A config path can be fixed or supplied through a normalized flag (`include/clasp/command.hpp:193`, `include/clasp/command.hpp:198`).

`applyExternalSources` reads an env-like scalar format and four structured formats with small in-header parsers: JSON with a nesting-depth guard, YAML, TOML, and INI/CFG (`detail/config_parse.hpp:48`, `detail/config_parse.hpp:94`, `include/clasp/command.hpp:3536`). It flattens keys into long-flag aliases, including bare, underscore, dotted, and `varName` forms (`include/clasp/command.hpp:3571`), then inserts validated multi and scalar values (`include/clasp/command.hpp:3613`). Process environment variables override config values; the access helper is the platform boundary (`include/clasp/command.hpp:3603`, `include/clasp/color.hpp:46`). Thus the documented runtime precedence is CLI, environment, config file, then default (`docs/guide/config.md:3`). State is file content and process environment read during a run; there is no daemon, database, or network source.

## 6. Presentation, Export, And Terminal Adaptation

Presentation turns resolved command/flag state into user-visible help, usage, version, Markdown, and roff output. Help rendering gathers visible commands and local/global flags, honors function or template overrides, and supports a small placeholder template language rather than Go templates (`include/clasp/command.hpp:1409`, `include/clasp/command.hpp:2356`, `include/clasp/command.hpp:2245`). Usage follows the same override chain (`include/clasp/command.hpp:1831`), while Markdown and manpage export are separate text protocols (`include/clasp/command.hpp:1460`, `include/clasp/command.hpp:1499`). Output sinks are inherited or locally overridden `ostream` references (`include/clasp/command.hpp:1862`).

The color adapter encapsulates terminal capability, ANSI sequences, themes, `NO_COLOR`, `TERM=dumb`, and Windows VT mode (`include/clasp/color.hpp:66`, `include/clasp/color.hpp:78`, `include/clasp/color.hpp:88`, `include/clasp/color.hpp:95`, `src/color.cpp:14`, `src/color.cpp:32`). Presentation decides whether to style output using the color owner's runtime mode and the adapter (`include/clasp/command.hpp:2065`, `include/clasp/command.hpp:2079`). Color mode/theme may also come from persistent CLI flags; raw arguments are pre-scanned only until a subcommand boundary, then parser values are applied after normal parsing (`include/clasp/command.hpp:106`, `include/clasp/command.hpp:2112`, `include/clasp/command.hpp:2136`). Text is the channel: `stdout`, `stderr`, caller-owned streams, ANSI, Markdown, and roff.

## 7. Completion Protocol And Shell Generation

Completion has two cooperating surfaces. At command-tree setup, `enableCompletion` installs a user-facing script generator plus hidden dynamic commands according to `CompletionConfig` (`include/clasp/command.hpp:1541`, `include/clasp/command.hpp:3891`). The generated scripts call those hidden commands through the shell's normal process invocation channel (`include/clasp/command.hpp:3912`, `include/clasp/command.hpp:3937`).

The dynamic path receives shell words as `argv`, resolves the command that would execute, consults traversal-aware flag metadata and callbacks, and emits values and descriptions (`include/clasp/command.hpp:2562`, `include/clasp/command.hpp:2601`, `include/clasp/command.hpp:2725`). Directives are a Cobra-compatible numeric bitmask (`include/clasp/command.hpp:39`); filename and directory helpers turn extensions or directories into directive-producing callbacks (`include/clasp/command.hpp:885`, `include/clasp/command.hpp:904`). Static generator output covers Bash/Zsh through one internal generator, plus Fish and PowerShell, with shell-specific escaping helpers (`include/clasp/command.hpp:1533`, `detail/shell_escape.hpp:132`, `include/clasp/command.hpp:3622`, `include/clasp/command.hpp:3777`). The protocol files are generated at runtime rather than checked in as a dedicated protocol source.

## 8. Consumer Verification And Documentation Contract

Examples are small executable demonstrations of the model, execution, typed values, completion, external sources, and documentation export (`examples/basic_example.cpp:7`, `examples/completion_example.cpp:6`, `examples/config_json_example.cpp:7`, `examples/docs_example.cpp:7`). Unit and integration tests directly call `Command` and `Parser`, inject streams, and execute the resulting CLI rather than testing private internals (`tests/completion.cpp:13`, `tests/config_parse_coverage.cpp:64`, `tests/execute.cpp:7`). CMake turns examples into external black-box tests and pins exact messages for Cobra-compatible behavior (`cmake/examples.cmake:6`, `cmake/examples.cmake:401`).

The documentation site is the human-facing projection of that contract. English and Chinese guides describe commands, flags, completion, config precedence, templates, and custom `Value` types (`docs/guide/index.md:3`, `docs/zh/guide/index.md:3`), while VitePress wires both locales and excludes raw review archives (`docs/.vitepress/config.ts:5`, `docs/.vitepress/config.ts:15`, `docs/.vitepress/config.ts:8`). The cross-language content is synchronized by intent, and this architecture page plus its glossary now provide the source-derived abstract model.

## Splitting Rationale

1. **Separate declarations from an invocation's decoded result.** `Flag` is retained command metadata (`include/clasp/flag.hpp:61`), while `Parser` records ordered runtime occurrences separately (`include/clasp/parser.hpp:950`). Mixing them would blur persistent tree ownership with per-run state.
2. **Keep command ownership and parent resolution in one invariant.** Moving a `Command` must rewrite every child's parent pointer; the custom move and `reparent` path exist because normal member-wise movement would leave dangling parents (`include/clasp/command.hpp:83`, `include/clasp/command.hpp:220`, `include/clasp/command.hpp:2557`).
3. **Resolve the executing node before constructing a parser.** `resolveForExecution` consumes command tokens and returns command-specific `argv` (`include/clasp/command.hpp:2954`, `include/clasp/command.hpp:2974`), while `Parser` then parses only that node's effective flags (`include/clasp/command.hpp:1310`, `include/clasp/command.hpp:1319`). This makes inherited semantics and command-local positionals independent.
4. **Make source precedence observable at the accessor boundary.** `getFlag` explicitly consults CLI, external multi, external scalar, and defaults in that order (`include/clasp/parser.hpp:223`), and docs expose the same precedence (`docs/guide/config.md:3`). A hidden merge layer would make override behavior hard to reason about.
5. **Apply custom `Value` callbacks after all source merging.** The contract says `set()` sees final effective values in occurrence order (`include/clasp/value.hpp:13`), and execution applies bindings only after external sources (`include/clasp/command.hpp:1359`, `include/clasp/command.hpp:3491`). Earlier callbacks would break config/env-aware custom types.
6. **Treat generated scripts and dynamic completion as one protocol, not four unrelated outputs.** All generated shells ultimately call configured `__complete`/`__completeNoDesc` commands (`include/clasp/command.hpp:3891`, `include/clasp/command.hpp:3912`, `include/clasp/command.hpp:3937`), while `completeWords` resolves context once (`include/clasp/command.hpp:2725`). Shell-specific generators can then vary only syntax and escaping.
7. **Isolate platform and text-format details.** Terminal capability is confined to `color` (`src/color.cpp:14`, `src/color.cpp:32`); numeric/Base64 primitives to `detail/value_parse.hpp` (`include/clasp/detail/value_parse.hpp:25`, `include/clasp/detail/value_parse.hpp:188`); and file syntax parsing to `applyExternalSources` (`include/clasp/command.hpp:3519`, `include/clasp/command.hpp:3536`). Command orchestration does not need each platform rule inline.
8. **Pin externally visible text through executable consumer contracts.** CMake builds examples and asserts exact Cobra-compatible help/error strings (`cmake/examples.cmake:401`, `cmake/tests.cmake:2495`, `cmake/tests.cmake:2505`), while tests exercise in-process behavior (`tests/execute.cpp:7`, `tests/completion.cpp:13`). This keeps compatibility concerns separate from implementation organization.
